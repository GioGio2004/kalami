Three words on the headline question: there is **no authentication bypass, no cross-tenant read, no code execution path and no secret in the client bundles**. The real risks are exam-integrity logic (results released too early, edits mid-exam, lost answers on a failed save) and operational gaps (no CI, no backups, no limits), not the security perimeter.

* **Browser**: all student and staff UI is client-rendered React talking to Convex over a WebSocket (`student/components/ConvexClientProvider.tsx`, `stuff/components/ConvexClientProvider.tsx`). The check engine runs in the browser for live ticks **and** again on the server at save/submit; the browser result is never trusted (`stuff/convex/model/learn.ts:633`, `:709-713`).
* **Vercel**: serves pages and runs `proxy.ts` (Clerk middleware). The student app has no API routes at all. The staff app has `/api/mcp` (bearer-only), the two `.well-known` metadata routes, and a 410 stub for the retired `/api/mcp/k/[key]`.
* **Convex**: the only database and the only place business rules run. Both apps connect to the same deployment. Crons: auto-submit every minute, deadline reminders every 5 minutes (`stuff/convex/crons.ts`).
* **Clerk**: one application for both apps; roles are **not** in Clerk — they are rows in `memberships` (`stuff/convex/schema.ts:57-69`). Clerk is also the OAuth authorization server for the MCP connector.
* **Not present** (verified by grep, see §3.1): ImageKit SDK/uploads, YouTube embeds, email, PWA/service worker, push, lectures/modules, group linking, file storage, analytics, error reporting, dark mode, CI.

### 2.3 Convex schema (16 tables)

`universities`, `users`, `memberships` (roles + student profile), `invites`, `courses` (join code), `courseStaff` (owner/assistant), `assessments`, `questions`, `answerKeys` (separate table, never returned to students), `enrollments`, `attempts`, `responses`, `codeComments`, `joinAttempts` (rate limit), `notifications`, `notificationRuns`, `auditLog`. All queries use indexes (no table scans) except `courses` for the super admin (`take(200)`). No file storage (`ctx.storage`) is used.

### 2.4 Authorization model

* Identity is always `ctx.auth.getUserIdentity()` → `users.by_tokenIdentifier` (`stuff/convex/lib/auth.ts:94-109`). The one exception is `mcp.*`, whose `token` argument is an HMAC credential resolved to a user and re-checked for a staff role on every call (`stuff/convex/lib/access.ts:41-61`).
* Student XOR staff: onboarding refuses staff (`users.ts:249-251`), invites refuse students (`invites.ts:176-181`); the super admin is exempt everywhere.
* Course access (`access.ts:81-106`): super admin → everything; `uni_admin` → courses of their university; otherwise a `courseStaff` row is required (owner edits, assistant reads + grades). Everyone else gets `NOT_FOUND`, so other people's courses are not even enumerable. Tenant isolation is test-backed (`stuff/convex/studio.test.ts:139-207`).
* Students only ever reach data through their own `userId` and an **active** enrollment in a **published** course (`model/learn.ts:131-144`); removed enrollments are honoured everywhere they matter.
* MCP agents get the same model functions with `via: "mcp"`, plus one extra rule: they may only touch **draft** assessments (`model/assessments.ts:160-171`). Publishing, deleting assessments, join codes and anything about students have no MCP function at all (`stuff/convex/mcp.ts:42-43`).

### 2.5 Sandbox and grading

* Editor: CodeMirror 6 with paste/drop blocked and counted in student mode.
* Preview: `<iframe sandbox="allow-same-origin" srcdoc=…>` — **no scripts, forms, popups or top navigation** (`stuff/components/sandbox/Preview.tsx:59`). A `<meta http-equiv="Content-Security-Policy">` restricting loads to data:/Google Fonts/the asset prefix is spliced into the document by regex (`buildPreview.ts:18-29`, `:72-81`; see M-1 for the bypass).
* Checks: parse5 (browser-identical tree) + css-select + an own cascade with user-agent defaults (`stuff/convex/lib/checks/page.ts`). Rules: exists / not_exists / count / text / attr / css / linked. No regex rule type; text matching is `includes`/`===`. Per-rule try/catch, no time budget (M-2).
* Hidden checks and solutions live in `answerKeys`; students receive hidden-check *labels* only with full results (`model/learn.ts:512-518`) and `checkResults` filtered by the `h` id prefix in score mode (`:503-509`).

## 4. Findings

Severity: **Critical** = exploitable now with real damage; **High** = will hurt a real exam or compromise accounts under realistic conditions; **Medium** = needs fixing before wider rollout; **Low** = hygiene. Confidence: *confirmed* (code path traced end to end) or *potential*.

### Critical — none

### High

**H-1 · Answer keys are released the moment a student submits when a quiz has no closing time (the default for quizzes).** Confirmed.
Evidence: `stuff/convex/model/learn.ts:173-182` — `case "full_after_close": return state === "closed" || assessment.settings.closesAt === undefined ? "full" : "none";` Default quiz settings are `resultsVisibility: "full_after_close"` with no `closesAt` (`model/assessments.ts:72-79`). With "full", `model/quiz.ts:171-181` returns `correctOptionIds`, the whole `acceptedAnswers` list and `explanation`; `model/learn.ts:512-518` returns hidden-check labels.
Impact: a student submits (even blank), reads the key, shares it with classmates who have not started; with `attemptsAllowed > 1` they retake with the key and the **best** score counts (`model/learn.ts:318`). `learn.test.ts:386-455` asserts this behaviour rather than guarding against it.
Reproduce (dev): publish a quiz with defaults + `attemptsAllowed: 2`; as a student call `learn.startAttempt`, `learn.submit`, then `learn.quiz` → `review[].correctOptionIds` present.
Fix (S, ~2 h): in `validateSettings` require `closesAt` when `resultsVisibility === "full_after_close"`, and in `visibleResults` return `"score"` while `closesAt` is undefined. Better: an explicit `resultsReleasedAt` set by a "Release results" button. Verify: adjust the test at `learn.test.ts:431` to expect no `review` before close.

**H-2 · A failed autosave silently discards every other answer queued in the same batch, and Submit proceeds anyway.** Confirmed.
Evidence: `student/components/quiz/QuizPlayer.tsx:101-115` — the batch is removed from `pending` (`:102`), the loop re-queues **only the failing item** and `return`s (`:111-114`); `flush` never rejects, and `submit` continues with `await flush(); await actions.submit();` (`:142-143`). Same shape in `student/components/tasks/TaskView.tsx:70-83` and `:130-135`.
Impact: on a slow network two or three answers share a batch; if the first fails (question edited/deleted mid-exam → `INVALID_INPUT`/`NOT_FOUND`, oversize essay, deadline passed) the rest are never sent, the navigator still shows them "answered" (local `values`), and "Yes, submit" grades without them, with only a red status label as warning.
Reproduce (dev): throttle the network, answer Q1 then quickly Q2 and Q3; have the lecturer edit Q1's options before the batch lands; Q2/Q3 are never saved; Submit grades without them.
Fix (S, ~3 h): re-queue every remaining item of the batch on error; make `flush` return `false`/throw; refuse to submit while `pending.size > 0` (show the unsaved question numbers); mark answers "confirmed" only when `savedAt` comes back. Add the `beforeunload` check for an in-flight batch (M-11). Verify: a Vitest/RTL test of `flush` with a rejecting save.

**H-3 · Published assessments with live attempts can be edited from the web; edits corrupt saved answers and scores, and nothing regrades.** Confirmed.
Evidence: `requireEditable` only blocks agents (`stuff/convex/model/assessments.ts:160-171`, decisive `:165`); the builder shows Edit/Delete/Move on published work (`stuff/components/studio/AssessmentBuilder.tsx:422-450`). `updateQuestion` regenerates option ids — the code says so (`model/questions.ts:280`, `:289-303`); `deleteQuestion`/`reorderQuestions` rewrite `order` (`:334-337`, `:371-373`) and the seeded shuffle ranks by index, so every in-flight student's question order changes; `attempts.maxScore` is a snapshot (`model/quiz.ts:260`) while grading uses live `question.points` (`model/learn.ts:712`); `recomputeScore` only re-sums stored `autoScore` (`:758-770`). STUDIO.md:150 lists this as still open.

### 5.2 Request model (estimates, not measurements)

Assumptions: a 60-minute quiz of 20 questions (18 auto-graded, 2 essays, no code question); 40 answer changes per student; 12 integrity reports; ~1 KB per question document, 0.25 KB per response, 0.5 KB per small document (user, membership, enrollment, attempt, assessment, course); 30 ms server time per function; everyone signed in beforehand. Code tasks are discussed separately.

| Simultaneous students | Function calls per exam | DB bandwidth today | After splitting `learn.quiz` (M-3) | Peak executions/s (start burst) | Avg concurrency (S16 limit 16) |
|---|---|---|---|---|---|
| 30 | ~3,000 | ~44 MB | ~17 MB | 0.5 | 0.02 |
| 100 | ~10,000 | ~145 MB | ~55 MB | 1.7 | 0.08 |
| 300 | ~30,000 | ~440 MB | ~165 MB | 5 | 0.25 |
| 1,000 | ~100,000 | **~1.45 GB** | ~0.55 GB | 17 | 0.8 |

Reading the table:

* **Function calls are not the constraint.** Even 1,000 students in one exam use 10 % of the free monthly allowance. At $2.20 per million the money is cents.
* **Database bandwidth is the first quota hit, and `learn.quiz` is the cause.** One 1,000-student exam exceeds the free 1 GB/month because every autosave re-reads and re-pushes the whole quiz (M-3). On Starter that is $0.30; on Free without a card it is a stop. Splitting the query cuts it by ~60–90 %.
* **Concurrency is fine on S16 for these sizes** as long as functions stay fast; the start burst (everyone pressing Start within two minutes) is the only spike, under 1 concurrent execution on average. Slow functions change this: a `saveCodeWork` that takes 300 ms because of a large file multiplies concurrency by 10.
* **The real ceiling on the Free/Starter plan is 1,000 concurrent sessions** — every open tab (students, lecturers, the dashboard) counts. 1,000 simultaneous exam takers is impossible without Pro (10,000); ~900 participants is the practical limit, with no headroom for a lecturer watching.
* **Code tasks are heavier**: ~400 saves per student-hour, each carrying the full files (2–10 KB typical, 250 KB max) plus a server-side parse and cascade, and `learn.task` echoes the files back. Measure before putting 300 students on a code task at once.
* **Vercel** is almost idle in this architecture: pages are static or client-rendered, data goes browser ↔ Convex directly; Vercel only serves page loads, Clerk middleware and MCP calls. Pro limits are not a concern at these sizes.
* **Clerk**: 1,000 students are far under 50k MRU. Two things to test, not assume: (1) the sign-in creation limit of 5 per 10 s **per IP** — a classroom behind one NAT must sign in before the exam (Clerk sessions persist), 300 students signing in at once from one IP would take ~10 minutes; (2) the Convex client refreshes the Clerk JWT roughly once a minute per tab, so 1,000 students on one campus IP produce ~17 token refreshes/s to Clerk — no documented per-IP limit for that endpoint, but it must be in the staging test.
* **Email (planned)**: a "new work" notice to 1,000 students exceeds Resend's free 100/day on the first course; budget Pro ($20/mo).

Registered vs active vs simultaneous: 1,000 registered and 50 lecturers cost nothing extra on any plan; what matters is simultaneous open tabs (sessions) and, per exam, the bandwidth per student (~1.4 MB today, ~0.5 MB after M-3).

## 6. Proposed designs

### 6.1 Autosave and sync

Goals: never lose an answer the student saw as "answered", fewer requests, no trust in the client's clock or storage, no change to the authorization or deadline rules.

1. **Local draft store (IndexedDB, per user and attempt).** Key `kalami:draft:<userId>:<attemptId>`. Entries: `{questionId, value, rev, updatedAt}`. Written synchronously on every change before the debounce; read on mount to overlay server answers where `rev` is newer. Cleared on submit, on sign-out (Clerk `signOut` hook) and on load when the stored `userId` differs from the signed-in one (shared devices). Treated as a cache, never as proof of when work happened: the server's `savedAt` is the only timestamp of record. **Never store** questions/options beyond the session, keys, review data or other students' anything; sessionStorage for review flags stays as is.
2. **Revisions instead of last-writer-wins.** Client keeps a per-question `rev` (monotonic int); `saveQuizAnswer` gains `rev` and the server stores it on the response and rejects `rev <= stored.rev` with a typed `STALE` error carrying the stored value. This fixes the second-tab overwrite (M-11b) and makes retries idempotent.
3. **Batching.** One mutation `saveAnswers([{questionId, value, rev}])` per flush instead of one per question; code files sent only when changed (`contentHash` per file; unchanged files omitted), bounded to the existing 5 × 50 KB.
4. **Debounce + maximum interval + backoff.** Keep 0 ms for choices and 900 ms / 1,500 ms for text/code, add a **maximum wait of 10 s** while dirty, and on failure retry with exponential backoff (1 s → 30 s cap, with jitter) rather than waiting for the next keystroke. Re-queue the whole batch on any error (H-2). Flush before navigation, on `visibilitychange: hidden`, and on the server deadline minus 5 s.
5. **Acknowledgements and indicators.** Three states shown as text, not icons alone: "Saved on this device" (draft written), "Saving…", "Saved to Kalami at hh:mm:ss" (server `savedAt`). The question navigator shows the server-confirmed state; a pending/failed question gets a distinct mark. Submit is refused while anything is unconfirmed, listing the question numbers; the student can press "Try again" or "Submit without them".
6. **Deadlines and late work.** The server stays the only clock: it returns `serverNow` with the quiz (M-4) and the client counts down from the offset. Policy for late-arriving offline work: accepted within the existing 15 s grace for **both** deadline kinds (H-4); anything later is refused and the student is told which answers were not accepted. Lecturers can still award points manually. No silent acceptance after the deadline, and no reliance on `beforeunload` for delivery — the draft store plus retry on next load is the guarantee; `beforeunload` only warns.
7. **Storage failures.** If IndexedDB is unavailable (private mode, quota), fall back to memory and show "Saved on this device" never — only "Saved to Kalami"; the retry loop still runs. Eviction between sessions loses only unsent drafts, which the retry policy keeps short-lived.

Expected effect at the request level (10-question quiz, 40 changes): ~40 save mutations → ~15–25 batched saves; `learn.quiz` re-runs 45 → ~5 after the split (M-3); integrity patches no longer invalidate the student query if counters move to their own table.

### 6.2 Rate limiting and abuse controls

Use the official `@convex-dev/rate-limiter` component (token bucket stored in Convex, enforced inside the mutation, so it is distributed and survives restarts). Key by **authenticated user id**, never by IP — classrooms share one IP. Add a second, coarser key per assessment for expensive work so one exam cannot starve another.

| Operation | Limit (per user unless noted) | Burst | Rationale |
|---|---|---|---|
| `learn.join` | existing 8 wrong / 15 min; add 30 calls / 15 min total | — | guessing + hammering |
| `learn.startAttempt` | 10 / min | 3 | double-clicks are already idempotent |
| `learn.saveQuizAnswer` / `saveAnswers` | 120 / min | 30 | honest clients ≤ 1/s with batching far below |
| `learn.saveCodeWork` | 60 / min | 15 | 1.5 s debounce → ≤ 40/min; plus a **payload cap of 5 × 50 KB and a `Page` work budget** |
| `learn.reportIntegrityCounts` | 12 / min | 6 | 10 s cadence |
| `learn.submit` | 5 / min | — | |
| grading mutations (staff) | 120 / min | 30 | |
| `questions.add` / MCP `add_questions` | 20 calls / 10 min per actor; the existing 50/call and 200/assessment stay | — | each call can run 20 variant checks |
| `mcp.*` total | 60 / min per lecturer | 20 | one agent loop |
| `create_course` / `create_assessment` (web and MCP) | 10 / h and 30 / h per actor; soft cap 500 courses per owner | — | lists truncate at `take(200)` today |
| `invites.create` | 50 / day per admin; one pending invite per email | — | |
| notification fan-out | bounded by enrollments (already batched 100); add 1 fan-out per assessment per kind (already) | — | |
| public `invites.getByToken`, `honesty.current` | 60 / min per IP at the edge (Vercel/Convex HTTP) if abused; cheap reads otherwise | — | |

Behaviour on limit: the mutation throws a typed `RATE_LIMITED` error with `retryAfterMs`; the autosave layer backs off (§6.1 item 4) and the UI shows "Saving slower than usual" — never discards. Expensive-path protection: grading is already spread by the scheduler (500 per minute); add the `Page` caps so a single 50 KB file cannot consume the 1 s budget. Server-side payload limits already exist for every field (§3.2) except the check-rule strings (L-6).
